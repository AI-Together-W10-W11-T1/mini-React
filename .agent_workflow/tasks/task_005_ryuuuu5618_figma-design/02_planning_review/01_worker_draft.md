## 먼저 코드로 확인한 엔진 사실 (계획의 전제)

| 확인한 것 | 결과 | 계획에 미치는 영향 |
| --- | --- | --- |
| `style` 객체 비교 | 항목별 `SET_STYLE`(`property` · `before` · `after`) 한 줄씩 (`diff.ts` `diffStyle`). 이름은 쓴 그대로(`background-color`) | 색을 바꾸면 버튼마다 배경 1줄, 글자색이 같이 바뀌면 +1줄 |
| `disabled` 같은 boolean 속성 | `true` → 속성 `""`, `false` → 속성 없음 → `SET_ATTR` 한 줄 (`button`은 DOM 프로퍼티 대상이 아님). 꺼진 버튼은 눌러도 `click`이 안 옴 (jsdom · Chromium 둘 다 실행해서 확인) | [↶] [↷]의 켜짐 · 꺼짐은 `SET_ATTR` 1줄, 꺼진 버튼 클릭 = 아무 일 없음 |
| `aria-pressed` | 불린 `false`를 주면 속성이 빠져 버림 → **문자열 `'true'` / `'false'`로** | 칩의 「지금 색」 표시를 문자열로 |
| `<input type="color">`의 `value` | `input`이라 DOM 프로퍼티(`SET_PROP`), 실제 값과 다를 때만 대입. 브라우저가 `#rrggbb` 소문자로 정리하고 형식 밖이면 `#000000`(jsdom · Chromium 확인) | 색 칸 값은 항상 소문자 hex, 상태에 이상한 값이 안 들어옴 |
| `input` 이벤트 | 엔진이 받는 이벤트 = `click` · `input`. 색 입력칸은 드래그하는 동안 `input`을 연달아 냄(`change`는 닫을 때, 엔진이 안 받음). Playwright `fill('#336699')`는 `input` + `change`를 보냄(실행 확인) | 색 입력칸은 `onInput`만, 연속 입력은 기존 「같은 칸 연속 = 한 단계」로 묶임 |
| 자식 안의 자식 컴포넌트 | `resolveComponents`가 끝까지 풂 (`Canvas` → `Button`과 같음) | `PropertyPanel` 안에서 `ColorPalette`를 불러도 됨 (Hook 없이 props만) |

## ④ 정해야 할 것 (질문 + 추천)

### ④-1 [중요] 글자 색 자동 기준 (FD-24) — 후보 3개

배경이 밝으면 검정, 어두우면 흰색으로 바꾸는 기준이다. 글자는 두 가지(흰 `#ffffff`, 먹 `#0a0b0d`) 중 하나로만 한다.

| 후보 | 방법 | 칩 8개 결과 (흰 글자 / 먹 글자) | 장단점 |
| --- | --- | --- | --- |
| **A. 대비가 큰 쪽 (추천)** | 배경과 흰색, 배경과 먹색의 명암 대비(WCAG 공식)를 각각 구해 **더 큰 쪽 글자색**을 쓴다. 경계는 `#777777`(흰) / `#787878`(먹) | 흰: `#0052ff` `#cf202f` `#0a0b0d` `#5b616e` / 먹: `#05b169` `#f4b000` `#a8acb3` `#eef0f3` | 두 글자색 중 더 읽히는 쪽을 항상 고른다 → 초록(`#05b169`)에서도 대비 7.0. 설명이 쉽다 (「둘 중 더 잘 보이는 쪽」). 계산이 조금 길다 |
| B. 체감 밝기 128 | `(R×299 + G×587 + B×114) / 1000`이 128 이상이면 먹, 아니면 흰 | 흰: `#0052ff` `#cf202f` **`#05b169`** `#0a0b0d` `#5b616e` / 먹: `#f4b000` `#a8acb3` `#eef0f3` | 한 줄이라 가장 단순하고 흔한 방법. 단점: 초록에 흰 글자(대비 2.8로 약함), 순빨강 `#ff0000`도 흰 글자(대비 4.0) |
| C. 상대 밝기 0.5 고정 | 사람 눈에 맞춘 밝기(0~1)가 0.5를 넘으면 먹 | 흰: `#0052ff` `#cf202f` `#05b169` `#0a0b0d` `#5b616e` **`#a8acb3`** / 먹: `#f4b000` `#eef0f3` | 기준이 눈에 쉬움. 단점: 중간 회색(`#a8acb3` 대비 2.3)에서 흰 글자가 안 읽힘 |

추천 A. 이유: 칩 8개 모두에서 글자가 가장 잘 읽히고, 「둘 중 더 잘 보이는 쪽」이라 발표에서 한 문장으로 설명된다. 정해지면 `color.test.ts`의 판정 표(경계 행)와 QA-36 · A23 기대값이 그 기준으로 바뀐다.

### ④-2 글자색을 어디에 담을까 — `style`(추천) vs 클래스

명세 FD-23은 「배경색을 `style`로 (색을 바꾸면 `SET_STYLE` 1줄)」인데 글자색도 같이 바뀌어야 한다.

| 후보 | 색을 바꿀 때 버튼 하나의 patch | 장단점 |
| --- | --- | --- |
| **X. 글자색도 `style`에 (추천)** | 글자색이 그대로면 `SET_STYLE` 1줄, 밝기 쪽이 바뀌면 2줄(배경 + 글자색) | 「색에서 나오는 모양은 모두 `style`, 크기 같은 종류는 클래스」로 규칙이 하나. 글자 색 판정 함수 결과를 그대로 넣음 |
| Y. 글자색은 클래스(`on-light` / `on-dark`) | 배경 `SET_STYLE` 1줄 (+ 밝기 쪽이 바뀌면 `class` `SET_ATTR` 1줄) | 명세의 「1줄」과 글자 그대로 가깝지만, 색 하나를 `style`과 클래스 두 곳에서 나눠 관리 |

(P-5 · 5b · 19의 캔버스 줄 수와 QA-39의 속성 변경 횟수가 이 결정에 따라 달라진다. 표는 X 기준으로 썼다.)

### ④-3 색 직접 고르기 칸에서의 키 규칙 — 넓힘(추천) vs 그대로

색 칸이 선택 상자에서 `<input type="color">`로 바뀌면서, 지금 코드는 이 칸을 **글자 입력칸으로 분류**한다 (글자가 아닌 `input`이면 전부 글자 입력칸으로 봄). 그대로 두면 색 직접 고르기 칸에 포커스가 있을 때 Ctrl+Z · Ctrl+Shift+Z가 **아무 일도 안 한다** (칸을 고르고 바로 Ctrl+Z를 누르는 흔한 동작).

- **추천**: 색 입력칸을 선택 상자 · 체크박스와 같이 취급 — Ctrl/Meta+Z = 앱 Undo, +Shift = Redo(브라우저 기본 동작 막음), Delete · Backspace는 무시. `keys.ts` 한 줄 + 테스트 (Dev-4, QA-A28). 명세 「단축키 Q18을 안 바꾼다」와 부딪히지 않게, Q18 ② 규칙(글자 입력이 없는 칸 = 앱이 Undo/Redo)의 대상에 새 입력 부품을 더하는 것이다
- 그대로: Dev-4와 QA-A28을 뺀다. 대신 색 칸에 포커스가 남아 있으면 Ctrl+Z가 먹통이라는 한계를 README에 적는다

### ④-4 override 칸 표시 색 (CSS만)

명세는 「기존 주황 선택 표시를 없앰」이라고 했는데, 지금 주황은 고른 것 표시와 **override 칸 표시(왼쪽 줄 + 연한 배경)** 두 곳에 같이 쓰인다. override 칸은 어떤 색으로?

- **추천**: 파랑 계열(왼쪽 파랑 줄 + 연한 파랑 배경) — 「장식 강조색은 파랑 하나」(FD-03). 다만 고른 것 표시와 색이 같아져서, 위치(고른 것 = 캔버스 · 레이어, override = 속성 패널 칸)로 구분된다
- 대안: 중립 회색 줄(`#5b616e`) — 강조색 하나를 지키고 구분도 쉬움. 대신 override가 덜 눈에 띔
- 테스트는 `override` 클래스 · ↻ 유무만 보므로 색을 정해도 코드 테스트는 안 바뀜 (QA-41의 「주황 0개」만 영향)

### ④-5 (확인만) 칩을 연달아 눌러도 한 단계

기존 규칙 「같은 대상 + 같은 칸이 연달아 바뀌면 한 단계」를 색에도 그대로 쓴다: 칩 A → 칩 B → 색 직접 고르기까지 Undo 한 번에 시작 색으로 돌아간다. 칩을 누를 때마다 한 단계로 하길 원하면 알려 달라 (명세의 동작 규칙을 바꾸는 일이라 이 task에서는 안 바꿨다).

### ④-6 (확인만) 현재 색 값 글자를 팔레트 판에 보인다
