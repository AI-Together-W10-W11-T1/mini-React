## 4. 주의사항 · 열린 질문
- **0.5단계 `types.ts` 변경 예정**: 주석 VNode 종류 추가, patch 한 줄 타입(종류 · 경로 · 전 · 후, Key 확장의 이동 포함), 경로 타입, History 기록 타입(VNode · 패치 · 역패치). 변경은 `types_changelog.md`에 남긴다.
- **기존 코드 유지**: 커밋 `5b55475`의 VNode 타입 · `h()` · `renderVNode` · 최소 페이지 · e2e는 결정 1(TEXT 객체)과 같은 방식이라 유지하고 고쳐 쓴다.
- **공백 · 주석을 남기므로** VNode 자식 번호 = 실제 DOM `childNodes` 번호. 편집창에서 들여쓰기만 바꿔도 "글자 바꾸기" patch가 생긴다 (알려 둔 비용).
- **편집창 글**: 뒤로 · 앞으로 때 저장한 VNode를 HTML 글로 바꿔 채운다 → VNode → HTML 글 변환이 필요하다 (공백 · 주석 그대로).
- **Patch 때 alert**: e2e는 dialog 처리를 해야 한다.
- **짝 검사 · 구조 비교**는 새로 만드는 코드라 시간 · 테스트가 늘어난다. 사용자 규칙은 "늦어지면 확장을 뒤에서부터 미룬다"이고, 검사기는 사용자가 정한 §5 정책(PRD 필수 아님)이다. 확장을 다 미뤄도 늦어지면 검사기를 줄일지 그때 사용자에게 묻는다.
- **역순 되돌리기가 성립하려면** patch 목록은 순서대로 하나씩 적용하고, 각 경로는 그 일을 실행하는 순간의 트리 기준이어야 한다.
- **Diff 시각화**: 삭제된 노드는 지우기 전에 위치를 재야 하므로, `patch`가 적용하는 노드 정보를 바깥(페이지)에 알려 주는 방법이 필요하다. DOM을 그리는 오버레이는 fixture 쪽에 둔다.
- **VNode 입력**(숫자 · 배열 · `null` · boolean, §5): 기존 `h()` 동작(문자열 · 숫자 → 글자, `null` · `undefined` · boolean 무시, 배열 평탄화)을 유지하고 phase2에서 다시 확인한다.
- **2.5단계 체크포인트 대상**:
  - "React는 History를 어떻게 하나"(사용자 질문, 결정 뒤로 미룸)
  - 피그마(고유 ID · 분수 위치) · 구글 문서(인덱스 보정) · 우리(역순 + key) 비교
  - 갈림길 정책(앞쪽 기록 버림)은 `추천안 수용 (이유 미기재)` → "왜 이걸 골랐나"
  - 보관 한도 50의 수치 이유
- **남은 일**: Phase 1 · 2가 끝나면 SVG 지원 리마인드. Phase 2 주제 후보: 피그마 같은 컴포넌트 시연(`<div>` + CSS 도형, 레이어 순서 바꾸기로 Key 시연).
