## 1. 목적과 적용 원칙

이 문서는 팀원 3명이 서로 다른 웹페이지와 구현 방식을 선택하면서도, 무엇을 구현했고 어떤 동작을 검증했는지 공통 기준으로 확인하기 위한 문서다.

각자는 요구사항과 테스트 케이스, 측정 지표를 확인하고 자신의 구현 범위와 검증 계획을 정한다. 개발 후에는 구현 결과와 테스트 결과, 측정 조건을 공유한다. 같은 화면이나 알고리즘을 만들 필요는 없다.

- **필수**: 원래 과제에서 요구한 핵심 기능과 이를 확인하는 테스트.
- **공통 참고**: 원문에 세부 동작이 정해져 있지 않아, 각자가 정책을 정하고 기록할 항목 및 권장 테스트.
- **선택 확장**: 핵심 기능 완료 후 자유롭게 추가할 기능.

공통 참고 항목은 원래 과제의 추가 필수 요구사항으로 간주하지 않는다. 서로 다른 정책의 결과는 해당 정책을 함께 보고 해석한다. 팀 전체의 합격 기준으로 추가하려면 개발 전에 함께 합의한다.

## 2. 구현 범위와 자유도

### 2.1 공통 필수 범위

- 실제 DOM을 Virtual DOM으로 변환한다.
- 이전·새 Virtual DOM을 비교하고, 변경된 부분만 실제 DOM에 반영한다.
- Phase 1의 실제 영역·테스트 영역과 Patch·뒤로가기·앞으로가기를 구현한다.
- 함수형 컴포넌트와 이를 감싸는 `FunctionComponent` 클래스를 구현한다.
- 루트 컴포넌트에서만 State와 Hooks를 사용한다.
- `useState`, `useEffect`, `useMemo`를 구현한다.
- Phase 2의 상태 변경 시 Phase 1의 Virtual DOM / Diff / Patch를 활용한다.
- 사용자 입력 또는 클릭에 따라 화면이 부분 갱신되는 웹페이지를 구현한다.
- 핵심 모듈의 단위 테스트와 화면 동작의 기능 테스트를 수행한다.
- 핵심 로직의 동작 원리와 실제 React와의 차이를 설명할 수 있어야 한다.

### 2.2 개인이 자유롭게 결정하는 사항

| 구분 | 선택 가능한 내용 |
|---|---|
| 웹페이지 | 주제, 화면 구성, 스타일, 데이터, 사용자 시나리오 |
| 알고리즘 | 트리 비교 방식, 노드 탐색, Patch 대상 식별·적용 순서, 목록 처리 |
| 내부 표현 | VNode 구조, Patch 구조, 상태 저장 및 이력 저장 방식 |
| 코드 구성 | 파일·모듈 구성, 공개 API, `h()` 등 VNode 생성 API |
| 편집 UI | HTML 입력창, 직접 편집 등 테스트 영역의 수정 방식 |
| 개발 도구 | 과제 제한에 부합하는 빌드·테스트·계측 도구 |
| 확장 | Key, Batching, 시각화, 성능 대시보드 등 |

VNode 필드명, Patch 명령 이름, Diff 전략, 폴더 구조를 통일하지 않는다. 비교할 때는 최종 DOM·상태·관찰 가능한 동작을 우선 확인한다. 테스트 공유가 필요하면 각 구현에 맞는 어댑터를 둘 수 있다.

### 2.3 기술 제한과 비필수 범위

- React, Vue 등 외부 UI 프레임워크는 사용하지 않는다.
- 렌더링·Diff·Patch·Hook의 핵심 로직은 직접 구현한다.
- 실제 React와 완전히 동일한 API·내부 동작은 요구하지 않는다.
- Fiber, Concurrent Rendering, Suspense, SSR, JSX 컴파일러, 라우터는 필수가 아니다.
- 자식 컴포넌트의 독립 상태·Hook 관리는 이번 과제 범위에 포함하지 않는다.
- 특정 주제의 앱, 성능 대시보드, 세 가지 렌더링 방식의 전체 앱 구현, 발표용 점수표는 필수가 아니다.

## 3. Phase 1 — Virtual DOM / Diff / Patch

### 3.1 필수 요구사항

구현 방식의 자유와 동작 명세의 구체성은 별개다. 아래 항목은 각각 독립적으로 검증할 동작을 정의하며, 자료구조·알고리즘·Patch 표현·편집 UI를 지정하지 않는다. **원문 명시**는 과제에서 직접 요구한 항목이고, **검증 구체화**는 그 기능의 정상 동작을 판정하기 위해 나눈 기준이다. 검증 구체화는 별도의 확장 기능을 추가한다는 뜻이 아니다.

|---|---|---|---|

| P1-02 | 텍스트 노드 변환 | 실제 DOM의 텍스트 내용과 자식 사이의 위치가 보존된다. | T-01 |

| P1-04 | 중첩 구조 변환 | 부모·자식 관계와 형제 순서가 보존된다. | T-01 |
| P1-05 | VNode 렌더링 | VNode로 생성한 DOM의 태그·텍스트·속성·자식 순서가 목표 구조와 일치한다. | T-02 |

| P1-11 | 노드 삭제 탐지·반영 | D-04의 대상 노드가 제거되고 나머지 구조가 목표 상태와 일치한다. | T-03 |
| P1-12 | 노드 교체 탐지·반영 | D-05의 노드 종류와 하위 구조가 목표 상태와 일치한다. | T-03 |
| P1-13 | 무변경 처리 | 이전·새 상태가 같으면 실제 영역에 불필요한 DOM 변경이 발생하지 않는다. | T-04 |
| P1-14 | 중첩 변경 처리 | 루트 아래 여러 단계에 있는 변경도 올바른 대상에 반영된다. | T-05 |
| P1-15 | 복합 변경 처리 | 한 번의 갱신에서 여러 종류의 변경을 반영한 최종 DOM이 목표 상태와 일치한다. | T-05 |

| P1-21 | 초기 테스트 영역 생성 | 실제 영역에서 읽은 VNode를 이용하여 테스트 영역을 렌더링한다. | T-07 |
| P1-22 | 테스트 영역 수정 | 태그·텍스트·속성·자식 구조를 수정할 수 있다. 수정 UI의 형태는 자유다. | T-07 |
| P1-23 | 최신 테스트 DOM 읽기 | Patch 실행 시 최신 편집 결과가 반영된 테스트 영역의 실제 DOM을 VNode로 변환한다. | T-07 |
| P1-24 | Patch 버튼 및 실행 흐름 | Patch 버튼을 제공하고, 클릭 시 이전·새 VNode의 차이를 이용해 실제 영역을 목표 상태로 갱신한다. | T-07 |
| P1-25 | 연속 Patch 기준 갱신 | 한 번 갱신한 뒤 다음 Patch는 직전 반영 상태를 기준으로 정확하게 동작한다. | T-07 |

| P1-27 | 과거 이력 보존 | 후속 편집·Patch로 이미 저장한 과거 상태의 내용이 바뀌지 않는다. | T-08 |
| P1-28 | 뒤로가기 버튼 | 뒤로가기 버튼을 제공하고, 이전 이력이 있을 때 클릭으로 해당 상태로 이동한다. | T-08 |
| P1-29 | 앞으로가기 버튼 | 앞으로가기 버튼을 제공하고, 다음 이력이 있을 때 클릭으로 해당 상태로 이동한다. | T-08 |
| P1-30 | 두 영역의 이력 동기화 | 이력 이동 후 실제 영역과 테스트 영역이 모두 선택한 상태를 나타낸다. | T-08 |
| P1-31 | 모듈 단위 검증 | DOM 변환·VNode 렌더링·Diff·Patch·History 동작을 단위 테스트로 검증한다. | T-01~T-08 |
| P1-32 | 화면 기능 검증 | 브라우저에서 편집 → Patch → 이력 이동 흐름의 결과를 기능 테스트로 검증한다. | T-07, T-08 |
| P1-33 | VNode 간 Diff | 실제 DOM을 다시 비교하는 것으로 대체하지 않고, 이전·새 VNode 두 개를 비교해 변경을 식별한다. 결과 표현은 자유다. | T-03, T-05 |
| P1-34 | Diff 결과의 DOM 반영 | 식별한 변경을 실제 DOM에 적용한다. 별도 Patch 목록이나 특정 반환 형식은 요구하지 않는다. | T-03, T-06 |

### 3.2 기본 변경 유형

원문의 다섯 가지 핵심 케이스를 검증하기 위한 공통 분류는 다음과 같다. 내부 Patch 표현이나 명령 이름은 자유다.

| ID | 변경 유형 | 예시 | 기대 결과 |
|---|---|---|---|
| D-01 | 텍스트 변경 | `A` → `B` | 해당 텍스트가 갱신된다. |
| D-02 | 속성 변경 | 속성 추가·수정·삭제 | 대상 요소의 속성이 새 상태와 일치한다. |
| D-03 | 노드 추가 | 자식 수 증가 | 올바른 위치에 노드가 추가된다. |
| D-04 | 노드 삭제 | 자식 수 감소 | 대상 노드가 제거된다. |
| D-05 | 노드 교체 | `div` → `section` | 노드 종류와 하위 구조가 새 상태와 일치한다. |

변경이 없는 입력, 중첩 변경, 여러 변경이 함께 발생하는 입력도 확인한다. 삭제 등으로 위치가 달라져도 다른 노드를 잘못 수정하지 않아야 한다.

부분 갱신은 전체 트리의 수학적 최소 편집 횟수를 보장한다는 의미가 아니다. 단순 텍스트·속성 변경에서는 대상 요소와 관련 없는 노드를 불필요하게 재생성하지 않는지 확인한다.

### 3.3 이력 정책 — 개인별로 정하고 기록

- 초기 상태를 저장하는 시점.
- 변경 없는 Patch의 이력 저장 여부.
- undo 후 새로운 변경을 적용했을 때 redo 이력의 처리.
- 첫·마지막 이력에서 이동 버튼을 눌렀을 때의 동작.
- 이력 이동 시 저장하지 않은 편집 내용의 처리.
- 이력 보관 한도 및 스냅샷의 이전 상태 보존 방법.

권장 기본값은 초기 상태 저장, 무변경 이력 생략, 새 분기에서 redo 제거, 경계 이동 무시다. 다른 정책도 가능하며 해당 정책에 맞는 테스트를 작성한다.

## 4. Phase 2 — Component / State / Hooks

### 4.1 필수 요구사항

Phase 1과 동일하게 원문 명시 사항과 검증 구체화를 구분한다. Hook의 핵심 역할은 필수이고, 원문에 없는 세부 API·실행 정책은 §4.2에서 별도로 다룬다. 기존 v2.0의 P2-01~P2-09는 아래 ID로 재분류했다.

| ID | 요구사항 | 수용 기준 | 관련 테스트 |
|---|---|---|---|
| P2-01 | 함수형 컴포넌트 | UI 컴포넌트를 함수로 구현한다. 래퍼 클래스와 함수형 UI 컴포넌트를 구분한다. | T-09 |
| P2-02 | 컴포넌트별 UI 구성 | UI를 기능에 맞는 컴포넌트로 나누며 각 컴포넌트가 자신의 UI를 표현한다. 주제·분할 방식·개수는 지정하지 않는다. | T-16 |
| P2-03 | 함수형 컴포넌트 래퍼 | 함수형 컴포넌트를 감싸는 `FunctionComponent` 클래스를 직접 구현한다. | T-09 |
| P2-04 | hooks 배열 | `FunctionComponent`가 상태 저장에 사용하는 `hooks` 배열을 갖는다. 슬롯의 내부 구조는 자유다. | T-10, T-11 |
| P2-05 | mount() | 최초 호출 시 컴포넌트의 초기 UI를 실제 DOM에 렌더링한다. | T-09 |
| P2-06 | update() | 상태 변경 후 컴포넌트를 다시 실행하여 변경된 UI를 반영한다. | T-09, T-15 |
| P2-07 | 루트 전용 상태 관리 | 앱의 변경 가능한 UI 상태는 루트 컴포넌트에서 관리한다. | T-16 |
| P2-08 | 루트 전용 Hook 사용 | Hook은 루트 컴포넌트에서만 사용한다. 잘못된 호출의 런타임 탐지·오류 발생 기능까지 필수로 요구하지 않는다. | T-16 |
| P2-09 | Stateless 자식 | 자식은 자체 State·Hook 없이 부모가 전달한 props로 UI를 구성하는 순수 함수다. | T-16 |
| P2-10 | props 전달 반영 | 루트 상태에 따라 자식 props가 바뀌면 자식의 UI 결과에도 반영된다. | T-16 |
| P2-11 | useState 초기 상태 | 최초 렌더링에서 선언한 초기 상태값을 사용할 수 있다. 지연 초기화 함수 지원은 별도 정책이다. | T-10 |
| P2-12 | useState 상태 유지 | 컴포넌트 함수가 다시 실행되어도 저장된 상태가 초기값으로 되돌아가지 않는다. | T-10 |
| P2-13 | 여러 상태의 구분 | 루트에서 여러 상태를 사용했을 때 각 상태값이 서로 섞이지 않는다. | T-11 |
| P2-14 | setter 상태 변경 | useState가 제공하는 setter로 상태를 변경할 수 있다. 함수형 업데이트·동일 값 처리 정책은 §4.2에서 정한다. | T-10, T-14 |
| P2-15 | 상태 변경 후 자동 갱신 | 실제로 상태가 변경되면 사용자가 별도 렌더·Patch 버튼을 누르지 않아도 화면이 갱신된다. 동기·비동기 스케줄링은 자유다. | T-14, T-15 |
| P2-16 | useEffect 구현 | 함수형 컴포넌트에서 부수 효과를 등록하고 선언한 실행 조건에 따라 실행할 수 있다. 구체적인 시점·cleanup 정책은 §4.2에서 기록한다. | T-12 |
| P2-17 | useMemo 구현 | 계산 결과를 저장하고 같은 의존성에서 재사용하며 의존성 변경 시 다시 계산한다. 비교 방법은 §4.2에서 기록한다. | T-13 |
| P2-18 | 새 VNode 생성 | 상태 변경 후 컴포넌트 실행 결과로 새 UI의 VNode를 생성한다. 특정 생성 API는 요구하지 않는다. | T-15 |
| P2-19 | Phase 1 Diff 재사용 | Phase 1에서 구현한 Diff를 활용해 이전·새 VNode를 비교한다. 이벤트 등 Phase 2에 필요한 확장은 허용한다. | T-15 |
| P2-20 | Phase 1 Patch 재사용 | Phase 1에서 구현한 Patch를 활용해 실제 DOM에 변경을 반영한다. | T-15 |
| P2-21 | 부분 업데이트 | 상태 변경 시 앱 전체 DOM을 매번 교체하는 것으로 대신하지 않고 필요한 변경을 반영한다. | T-06, T-15 |
| P2-22 | 사용자 인터랙션 페이지 | 자유 주제의 웹페이지에서 사용자 입력 또는 클릭으로 상태와 화면이 변경된다. 입력과 클릭 모두를 의무화하지 않는다. | T-14 |
| P2-23 | Hook 단위 테스트 | useState·useEffect·useMemo를 각각 검증하고, 선언한 정책에 맞는 기대 결과를 확인한다. | T-10~T-13 |
| P2-24 | 화면 기능 테스트 | 실제 사용자 동작 후 앱의 상태와 표시 결과가 일치하는지 확인한다. | T-14, T-16 |

`useEffect`·`useMemo`의 이름만 있는 빈 구현은 충족으로 보지 않는다. 등록한 부수 효과 실행 및 계산 결과 재사용을 각각 확인해야 한다. 반면 실제 React와 동일한 모든 Hook 경계 동작, 함수형 setter, 자동 Batching, `unmount()` API, 자식 Hook 호출 감지 기능은 원문 필수로 추가하지 않는다.

### 4.2 Hook 세부 동작 — 공통 참고

원문은 Hook의 상세 API를 모두 정하지 않는다. 아래는 구현·테스트 시 참고할 권장 동작이며, 채택 여부와 차이를 각자 기록한다.

| Hook | 권장 동작·검증 항목 |
|---|---|
| `useState` | 최초 초기화, 여러 상태 슬롯 구분, 값 기반·함수형 갱신, 동일 값 갱신 정책 |
| `useEffect` | DOM 반영 이후 실행, 의존성 생략 시 매 렌더 후 실행, `[]`는 최초 실행, 의존성 변경 시 cleanup 후 재실행 |
| `useMemo` | 최초 계산, 같은 의존성에서 캐시 재사용, 변경 시 재계산, 의존성 생략 시 매 렌더 재계산 |
| 의존성 비교 | `Object.is`를 기본 참고 기준으로 사용 |
| Hook 호출 | 렌더 간 호출 순서를 유지하고, 허용하지 않는 호출의 처리 정책 기록 |
| 해제 | cleanup을 지원하면 `unmount()` 또는 동등한 해제 경로와 테스트 제공 |

Batching은 선택 과제다. 기본 상태 테스트는 최종 상태와 화면의 일치를 확인한다. 렌더링 횟수는 스케줄링 정책과 함께 기록하며, Batching 미구현을 실패로 판단하지 않는다.

### 4.3 이벤트 및 입력

앱에 필요한 이벤트의 등록·변경·제거를 처리한다. 재렌더링으로 같은 이벤트가 중복 실행되지 않는지 확인한다.

입력 요소를 사용하는 경우 `value`, `checked` 등 필요한 DOM 프로퍼티의 지원 범위를 기록한다. 관련 없는 상태 갱신으로 입력 노드가 재생성되거나 입력값·포커스가 사라지지 않는지 확인한다. 커서·선택 영역은 앱이 의도한 동작을 기준으로 검증한다.

## 5. 지원 범위 및 예외 정책

각자 아래 항목을 지원·미지원·제한 지원으로 구분한다. 단, 필수 요구사항인 일반 HTML 요소·텍스트·속성·중첩 구조와 기본 변경 처리를 미지원으로 선언하여 제외할 수는 없다. 공통 테스트를 비교할 때 지원 범위가 다른 결과를 동일하게 취급하지 않는다.

| 항목 | 기록할 내용 |
|---|---|
| 트리·노드 | 단일·복수 루트, 빈 트리, 텍스트, 공백, 주석 처리 |
| 태그·속성 | HTML·SVG 범위, 속성 삭제, boolean 속성, style 처리 |
| VNode 입력 | 숫자, 배열, `null`, boolean 등의 처리 |
| 목록 | 위치 기반·Key 기반 여부, 항목 동일성 및 재사용 기준 |
| 입력·이벤트 | 지원 이벤트, DOM 프로퍼티, 핸들러 교체·해제 |
| HTML 편집 | 파서의 자동 보정, 미지원 입력, 실행 가능한 HTML의 처리 |
| 오류 | 오류 표시, 정상 상태 보존 여부, 복구 방법 |

HTML 편집 기능은 사용자 입력을 실행하는 기능이 아니다. 스크립트·이벤트 속성 등 실행 가능한 입력의 차단 또는 격리 방식을 정하는 것을 권장한다. 이는 원문에 별도 명시된 보안 기능 요구사항은 아니다. 지원하지 않는 입력은 처리 정책을 명시한다.

노드 참조 보존은 비교 전략과 함께 판단한다. 위치 기반 비교에 Key 기반 항목 이동의 참조 보존까지 요구하지 않는다. Key를 지원하는 구현은 삽입·삭제·재정렬 후 같은 Key의 노드가 유지되는지 추가 검증한다.

- 속성 및 이벤트 제거, 핸들러 교체 후 중복 호출 방지.

- Memo 의존성 생략 및 의존성 비교의 경계 조건.

- Key·Batching 등 선택 확장의 동작.

### 6.3 테스트 케이스 기록 형식

| 항목 | 기록 내용 |
|---|---|
| 테스트 ID | 위 공통 ID 또는 개인 확장 ID |
| 근거 | 필수 요구사항 / 개인 정책 / 선택 확장 |
| 초기 조건 | 초기 DOM, 상태, 데이터 |
| 수행 동작 | 함수 호출, 입력, 클릭, 이력 이동 등 |
| 기대 결과 | 최종 DOM·상태, 호출 횟수, 유지할 노드 참조 등 |

| 실행 방법 | 명령어 또는 수동 재현 절차 |

필수 기능의 미구현은 해당 없음으로 처리하지 않는다. 선택 기능과 지원 범위 밖의 테스트는 제외 이유를 기록한다. 테스트 개수만 비교하지 않고, 어떤 요구사항을 검증했는지 함께 확인한다.

## 7. 공통 측정 지표

성능은 알고리즘과 구현 특성을 이해하기 위한 자료다. 초기에는 특정 시간·점수로 일괄 합격선을 두지 않는다. 기능 정확성을 먼저 확인하고, 측정 조건과 함께 결과를 공유한다.

| ID | 지표 | 측정·해석 기준 |
|---|---|---|
| M-01 | 기능 테스트 결과 | 필수·정책·확장별 통과/실패/미구현 수와 대상 테스트 ID |
| M-02 | 실제 DOM 작업 | 생성·삽입·삭제·교체·텍스트·속성 변경 등 집계 단위를 명시 |
| M-03 | 노드 참조 유지 | 보존 대상으로 정한 기존 노드 중 같은 참조가 유지된 수 / 대상 수 |
| M-04 | VNode 생성시간 | 새 UI 표현을 만드는 데 걸린 시간 |
| M-05 | Diff 시간 | 이전·새 VNode 비교에 걸린 시간 |
| M-06 | Patch 시간 | 실제 DOM에 변경을 적용하는 데 걸린 시간 |
| M-07 | 전체 처리시간 | 상태 변경 처리 시작부터 DOM 반영 완료까지의 시간 |

`MutationObserver`의 레코드 수는 실제 DOM API 호출 수와 같지 않다. 작업 카운터·관찰 레코드·추가 또는 제거된 노드 수를 구분하여 보고한다. 복합 Patch 한 개를 다른 구현의 DOM API 호출 한 개와 같은 단위로 비교하지 않는다.

`performance.now()`로 측정한 DOM 반영 완료까지의 시간은 화면 표시 완료 시간이 아니다. 사용자 응답시간·레이아웃·페인트 비용을 추가 측정하면 도구와 측정 구간을 명시한다. `requestAnimationFrame` 콜백만으로 페인트 완료를 단정하지 않는다.

개발시간·LOC·번들 크기는 선택 기록 항목이다. 개인별 경험과 도구 사용 차이가 있으므로 단독 순위 기준으로 사용하지 않는다.

| B-06 | 연속 상태 변경 | 최종 상태, 렌더 횟수, 처리시간 |
| B-07 | 개인 앱 대표 동작 | 실제 사용 시 상태·화면 일치와 입력 안정성 |

목록 재정렬, 대규모 데이터, 계산 캐싱, Batching 비교는 선택 시나리오다. 노드 수·항목 수·트리 깊이를 명시하고 혼용하지 않는다. 예를 들어 항목 1,000개는 DOM 노드 1,000개와 다르다.

### 8.2 공정하게 비교하기 위한 조건

- 개인 앱 결과는 해당 앱의 특성을 설명하는 자료로 사용한다. 서로 다른 화면의 시간만으로 알고리즘 우열을 판단하지 않는다.
- 구현 간 직접 비교를 원하면 동일한 초기 트리·데이터·변경 동작의 작은 공통 fixture를 사용한다. 전체 앱이나 디자인을 통일할 필요는 없다.
- 브라우저·버전·기기·화면 크기·CPU 제한·빌드 모드를 기록한다.
- 반복 측정 전 상태를 초기화하고, 초기 렌더링과 업데이트를 분리한다.
- 계측 패널 등 비교 대상 밖의 DOM 변경과 로그 출력을 측정에서 제외하거나 조건을 통일한다.
- 권장 반복 기준은 준비 실행 5회, 측정 30회 이상이다. p50·p95와 반복 횟수를 기록하며, 다른 조건을 사용하면 함께 적는다.
- 반복 중 오류가 발생한 실행을 설명 없이 제외하지 않는다.

전체 DOM 교체·직접 DOM 갱신과의 비교는 선택 실험이다. 수행하면 같은 fixture와 측정 구간을 적용한다. Virtual DOM이 항상 빠르다는 결론을 전제로 두지 않는다.

## 9. 개인별 결과 공유 양식

각자 아래 내용을 짧게 정리한다.

1. **웹페이지**: 주제, 대표 사용자 동작, 실행 방법.
2. **구현 범위**: 필수 요구사항 충족 여부, 지원·미지원 범위, 선택 확장.
3. **설계 선택**: VNode·Diff·Patch·Hooks의 구조와 알고리즘을 선택한 이유.
4. **정책 차이**: History, Hook, 이벤트, 입력, 목록 처리의 세부 동작.
5. **테스트**: 테스트 ID별 결과, 실패와 제한 사항, 실행 방법.
6. **측정**: 시나리오·데이터·환경·집계 단위·반복 횟수·실제 결과.
7. **해석**: 장점, 비용, 개선할 부분, 실제 React와의 차이.

측정하지 않은 수치는 결과로 제시하지 않는다. 서로 다른 조건의 결과는 차이를 밝히고 해석한다.
